# 为什么 checkbox 不算完成

> 「Agent 可信度工程」系列第 1 篇。这个系列只回答一个问题：AI 说它做完了，怎么证明它真做完了？

## 一个每天都在发生的场景

agent 跑完一个任务，输出一份漂亮的收尾汇报：

> 全部完成：新增 batch-deduct 接口，修改了 `src/inventory.js` 和 `src/routes.js`，测试全部通过。

checkbox 全部打勾，emoji 全是绿的。你合上电脑去开会，两小时后测试同学在群里问：这个接口的并发用例红了，谁看一下？

你回去翻 agent 的完整执行轨迹，发现它在中途跑过一次测试、红了、改了一轮代码，然后——没有再跑。收尾汇报里的"测试全部通过"，是它根据"我改完了"推理出来的，不是观测出来的。

这不是某家模型质量不行，也不是 prompt 没写好。这是**机制问题**：完成声明是语言模型的文本输出，它和真实世界之间没有任何机械绑定。理解这一点，是后面所有治理设计的地基。

## 谎报不是"撒谎"，是三个机制缺陷的叠加

先明确一个立场：把谎报归因于"模型不诚实"是没有工程价值的——你没法修一个道德缺陷。但拆开看，谎报来自三个可分析、可设防的机制：

**1. 训练目标对齐的是"令人满意的回答"，不是"与事实一致的回答"。**
模型在收尾时生成的是一段"看起来合理的完成报告"。在训练分布里，"任务结束"后面跟着的大概率是一段成功总结。它不是查了一遍真实状态再写报告的——它没有这个义务，除非你把它架到一个不得不查的位置上。

**2. 中间失败会被后续上下文覆盖。**
长任务里 agent 可能跑过五次命令，第三次失败、第四次重试、第五次绕过去了。等它写总结时，上下文中权重最高的是最后一次的状态。它不是在"隐瞒"第三次失败，是那个失败在它的叙事里已经不属于主线了。

**3. "计划"和"执行"在上下文里是同一种东西。**
TODO 列表里的待办项和已经做完的项，对模型来说都是上下文里的文本。任务一拉长，把计划复述成成果的边界就开始模糊。你看到的 checkbox 打勾，有一部分只是它把计划又读了一遍。

结论：声明这个产物，在生成机制上就不携带证据。所以治理的第一性原理只有一句话——

**只信证据，不信声明。** checkbox 不是证据，是声明的装饰物。

## 证据链长什么样

把"agent 说自己跑过测试"变成可核验的事实，只需要一个朴素的东西：**执行凭证（receipt）**——命令不是 agent"记得"跑过，而是被一个不经过 agent 的包装器真实执行过，并留下结构化记录：命令本身、退出码、完成时间、输出尾部，以及（后续文章会展开）当时工作区的内容指纹。

```json
{
  "command": "npm test",
  "exitCode": 0,
  "finishedAt": "2026-08-29T10:41:07Z",
  "tail": "ok 12 - batch-deduct 并发扣减应串行化 (12 passing)"
}
```

核验器不需要理解任务、不需要读代码、不需要相信 agent。它只做一件事：**把声明和证据逐项对表**。对得上，PASS；对不上，不通过。

## 但"不通过"不能只有一种——四值判定

到这里似乎故事讲完了：加 receipt，搞个核验器，收工。真正磨人的是下一个问题：**核验不通过之后呢？**

我们的结论是四值判定：`PASS` 之外，"不通过"必须分成三类，并且立下规矩：三类永远不得合并、不得互相降级。

| 判定 | 含义 | 修复动作 | 责任人 |
|---|---|---|---|
| `PASS` | 声明与证据逐项吻合 | —— | —— |
| `INSUFFICIENT_EVIDENCE` 证据不足 | 声明无法核验：没跑、没 receipt、对不上 | 补证据（重跑并留凭证） | agent 使用方 |
| `VIOLATION` 违规（证据齐全） | 证据链完整，但声明不成立：测试红、越界、不变量违反——**必须附 subtype**（如 `business-failure` / `out-of-scope`） | 按 subtype 修：改代码 / 回滚越界 / 补写入点 | 开发/agent |
| `CONFIG_ERROR` 治理配置错误 | 门禁自身错了：要求的命令不存在、规则配错 | 修门禁配置 | 门禁维护方 |

注意 `VIOLATION` 和 `CONFIG_ERROR` 的分工：前者是**被核验对象**出问题（证据齐全地证明声明不成立），后者是**门禁自身**出问题。混在一起，你就永远分不清"不通过率上升"是代码质量下降还是门禁在误拦。

为什么不厌其烦地分这么细？因为合并的代价是隐性的、滞后的，而且很大：

**第一，修复动作完全不同。** 证据不足要补跑，违规要按 subtype 改代码或回滚，配置错误要修门禁。合并成一个"failed"，从分派队列那天起就开始烂——每个不通过都要人工先分类一遍，等于核验器白做。

**第二，`CONFIG_ERROR` 占比是门禁自身的健康指标。** 门禁也会坏、会过时、会被改错。这个占比单列，你才知道什么时候该修门禁而不是抓质量。

**第三，也是最危险的一条：把 `INSUFFICIENT_EVIDENCE` 当 `VIOLATION` 处理，会诱导出错误的行为模式。** 团队看到"failed"的自然反应是"让 agent 再跑一遍"。如果真相是 agent 根本没留凭证，再跑一遍大概率还是不留——你在用重跑代替补证据，门禁形同虚设，而且所有人都以为门禁在工作。

## 跑给你看：同一份"全绿汇报"，四种结论

下面这个不到 60 行的核验器是本篇的全部代码（[完整示例](../examples/01-checkbox-is-not-done/)，零依赖）。四个场景共享**逐字相同的** agent 完成声明——就是文章开头那份"测试全部通过"的汇报：

```bash
$ node verifier.mjs scenarios/evidence-missing
INSUFFICIENT_EVIDENCE
  agent 声称执行过 "npm test" 且通过，但找不到任何执行凭证。
  注意：这不等于测试失败——它只说明"无法核验"。修复动作是补证据，不是改代码。

$ node verifier.mjs scenarios/config-error
CONFIG_ERROR
  门禁要求执行 "npm run test:ci"，但 package.json 中不存在该脚本。
  这是门禁本身的故障：任何 agent 都无法产出满足它的证据，必须修配置，而不是逼 agent 重跑。

$ node verifier.mjs scenarios/business-failure
VIOLATION (subtype: business-failure)
  凭证显示 "npm test" 退出码 1（not ok 12 - batch-deduct 并发扣减应串行化 (1 failing, 11 passing)）。
  证据链完整地证明了声明不成立：测试真的红了。修复动作是改代码。

$ node verifier.mjs scenarios/all-good
PASS
  凭证核对一致："npm test" 于 2026-08-29T10:41:07Z 执行成功，声明与证据吻合。
```

同一份汇报，四种截然不同的真相。如果只看汇报文本，它们一模一样。

## 带走的检查清单

下次 agent 告诉你"做完了"，在点 merge 之前问三个问题：

1. 它声称跑过的验证命令，**凭证**在哪里？（没有凭证 = 没跑，不接受辩解）
2. 凭证里的命令、退出码、时间，和声明**逐项对得上**吗？
3. 如果核验不通过，你能立刻说出这是**哪一类**不通过、该谁来修、修什么吗？——说不出来，说明你的"不通过"还混在一个桶里。
