# 两个生产事故的复盘：提示词约束防不住"没人意识到自己违反了约束"

> 「Agent 可信度工程」系列第 3 篇。前两篇讲了声明不可信、门禁要 fail-closed。这一篇回答一个更尖锐的问题：**门禁该检查什么？** 答案是从事故里长出来的。以下两个事故基于真实经历，业务场景与代码均以合成场景重现，只保留错误模式结构。

两个事故的共同点值得先说出来：**错误都发生在 agent（和审查人）的认知盲区里。** 没有任何一方"明知故犯"，这正是提示词约束的极限——你只能约束被意识到的东西。

## 事故 A：无人写入的字段

**现象。** 一个数据导出功能上线后，审计校验整批不通过：每条记录都要求带"操作人"字段，而导出数据里这个字段全部为空。模块整体不可用，回滚。

**排查结果让所有人沉默：这个字段没有任何代码路径写入过。** 不是写错了，是没人写。

**机制。** 功能被拆给两个 agent 并行开发：一个负责记录创建，一个负责导出。任务拆分文档里写着"记录需包含操作人"，但在执行中：

- 负责创建的 agent 实现了一个"干净"的记录结构——它的局部测试只断言自己写入的字段，全绿；
- 负责导出的 agent 假设字段"上游会写"，导出逻辑直接透传——它的局部测试用构造好的假数据，也全绿。

每个 agent 的局部 diff 单独 review 都挑不出毛病，声明也都"如实"——它们各自确实完成了自己理解的任务。缺失落在**责任缝隙**里：一个字段的写入，不属于任何一个子任务的局部视角，只属于全局。

**教训。** 这类缺陷靠 review 单 diff 永远抓不住，需要的是**全局不变量核验**：不看任何单个 diff，直接问"这个字段在交付范围内存在写入点吗"。36 行的检查器（[完整示例](../examples/03-production-incidents/write-point-check.mjs)）在合成复现里的输出：

```
VIOLATION (subtype: invariant-missing)  字段 "operator" 在整个交付范围内没有任何写入点。
  每个 agent 的局部 diff 都自洽、局部测试都通过——但合起来模块不可用。
  这类缺失只有"全局不变量"核验能抓到：不看单个 diff，问"写入点存在吗"。
```

提示词约束在这里为什么无效？我们确实在任务说明里写了"记录需包含操作人"。但两个 agent 都真诚地认为自己遵守了——创建方认为导出方会补，导出方认为创建方已写。**约束被"意识到"的前提是约束落在某个执行者的视野内，而字段写入恰好落在两个视野的缝隙里。**

## 事故 B：被兜底吞掉的 404

**现象。** 线上告警：某接口 INTERNAL_ERROR 率持续爬升。运维按"系统故障"处置：查负载、查依赖、重启——全部无效。几个小时后才定位到真相：上游有人持续查询一批不存在的编码，正确的响应本应是"不存在"（404 语义），但被代码里的兜底逻辑统一包装成了 500。

**机制。** 出错处理代码是 agent 写的，它按训练里最强的"健壮性"惯性加了一个兜底的 try/catch：所有异常统一转成"系统繁忙"。这个写法在代码评审里甚至显得专业——接口永不泄漏内部错误。但效果是：

- 调用方无法区分"你查的东西不存在"（改请求）和"系统真挂了"（等待/告警）；
- 监控上只剩 INTERNAL_ERROR 一个信号，真实病因被压平；
- 运维被引向完全错误的处置路径，MTTR 从分钟级变成小时级。

**教训有两条，一条给测试，一条给门禁。**

给测试：**断言错误类型，不要只断言"会报错"。** "输入非法时应抛错"这种测试在兜底版面前照样通过——它确实抛错了。只有断言到错误码/错误类型，掩盖才会现形：

```
兜底版（agent 交付）: 抛出 code=INTERNAL_ERROR → 门禁断言[错误类型应为 NOT_FOUND] FAIL
透传版（修复后）: 抛出 code=NOT_FOUND → 门禁断言[错误类型应为 NOT_FOUND] PASS
```

（[完整示例](../examples/03-production-incidents/error-masking.mjs)，含正确写法：已知业务错误原样透传，只兜底真正的未知异常。）

给门禁：把"已知业务错误必须透传类型"变成静态检查项——catch 块吞掉一切且统一改写错误码的写法，在提交时就拦下，而不是等监控告警。这类规则属于第 1 篇四值判定里 `CONFIG_ERROR` 对应的门禁配置侧：门禁的规则库，就是这么一条一条从事故里长出来的（第 5 篇详述）。

## 两个事故的共同结构

把两个事故叠在一起看，模式非常清晰：

1. **错误的引入者没有恶意、没有疏忽，甚至局部视角下"做得很好"。** 事故 A 里每个 agent 测试全绿；事故 B 里兜底写法本身是种常见风格。
2. **提示词约束失效的原因不是措辞，是认知盲区。** 约束要生效，必须先被意识到；而这两个错误恰恰都发生在没人意识到的维度上。
3. **抓住它们的都是场外机械核验**：一个问"写入点存在吗"，一个问"错误类型还在吗"——都不依赖理解任务意图，只核对不变量。

所以门禁规则的正确来源不是设计时的头脑风暴，而是事故后的沉淀：**每个生产事故复盘结束时，必须回答一个问题——"哪个机械核验本可以拦住它？"然后把它加进门禁。** 答不出来的事故，等于白交了学费。

## 带走的检查清单

- 任务拆给多个 agent 时，列出所有**跨子任务的全局不变量**（字段写入点、接口契约、错误码表），交付时逐条机械核验；
- 评审 agent 写的错误处理代码时，先问：这个 catch 吞掉了哪些类型？调用方还能区分病因吗？
- 测试里凡是断言"报错"的地方，追问一句：断言到**类型**了吗？
- 每个事故复盘的固定收尾动作：新增一条门禁规则 + 一个回归测试。
