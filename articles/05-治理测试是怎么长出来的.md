# 1000+ 治理测试是怎么长出来的

> 「Agent 可信度工程」系列第 5 篇，也是收尾。前四篇建了证据、门禁、规则、归属。最后一篇回答：**约束 agent 的代码，自己靠什么约束？**

## 治理代码是放大器，没有"再下一道防线"

业务代码出 bug，影响一个功能；门禁代码出 bug，放行的是**所有 agent 的所有产出**。治理体系是最后一条防线——它后面没有任何东西兜底，所以它的测试密度必须高于业务代码，这不是洁癖，是位置决定的。

1000+ 治理测试听起来像规划出来的工程质量。不是。回头看构成，大致是三类（比例为示意）：

- **事故回归（约四成）**：每个生产事故复盘的固定收尾动作——"哪个机械核验本可以拦住它？"（第 3 篇），答案落成规则，同时落一个回归测试。规则会被重构，测试保证事故不复发。
- **绕过事件沉淀（约四成）**：每次发现 agent 钻了门禁区（skip 口子、时间戳伪装、指纹外的语义改动），堵口子的同时加一个"这种钻法永远失败"的测试。第 2 篇的零 skip 原则背后就躺着一排这样的测试。
- **规则演进护航（约两成）**：门禁规则本身变更时，先写"新规则在旧场景下不得误判"的测试，再改规则。

注意构成：**八成测试是事后长出来的，不是事前设计出来的。** 这不是耻辱，是治理系统的正确生长方式——攻击面是 agent 在真实使用中探索出来的，没人能坐在桌前想全。

## 教训：一个语义散布三处

1000+ 测试也防不住所有问题，其中最贵的一次教训值得单独讲。

我们收紧过一条门禁规则：交付物的测试凭证从"有 receipt 即可"升级为"receipt 必须绑定改动指纹"。改动评审通过、上线——然后门禁开始自相矛盾：同一份交付，配置核验说不合格，校验脚本放行，团队文档里写的还是更早的"建议保留凭证"。

原因很丢人：这条语义在系统里**存在三份**——配置文件一份、校验脚本里硬编码一份、文档里一份。改的人只改了配置。后续影响比"一次误判"严重得多：团队开始不信任门禁的判定（"它自己又打架了"），而 agent 那边，如第 2 篇所说，会精准记住最松的那个裁判。

最小复现（[完整示例](../examples/05-governance-tests/single-source-demo.mjs)，44 行）：

```
版本 A：同一规则散布三处
  配置说:   需要 receipt + 指纹 → 这份交付 不放行
  脚本说:   有 receipt 就行     → 这份交付 放行
  文档说:   提交前请确保跑过测试（建议保留凭证）
  → 同一份交付，三个裁判三种说法。agent 会记住最松的那个。

版本 B：单一事实源（rules.json），校验与文档同根
  校验器: 这份交付 不放行（缺指纹）
  生成文档: 提交前必须提供测试凭证，且凭证须绑定改动指纹。
  → 规则改一处，校验器和文档同时变，矛盾在结构上不可能存在。
```

修复不是"下次改三处时小心点"——人不可靠，要靠结构：**规则只存在一个文件里，校验器从它读，文档从它生成。** 从此"语义有几处副本"本身成了一条门禁自查项。

这次教训还有个副产品，就是本系列第 1 篇那套四值判定：`CONFIG_ERROR` 之所以单列、不得合并降级，直接动机就来自这里——门禁自相矛盾的那段时间，所有"不通过"里混着大量门禁自身的误判，不分出来，团队连"该不该信门禁"都回答不了。

## 治理测治理

收个尾：门禁改动本身走什么流程？我们的规矩是——**改门禁规则的 PR，必须附带规则变更测试，且触发全量治理回归套件。** 用治理体系自己的机制治理治理体系自己。第 4 篇讲的 receipt、scope 核验，对门禁仓库的改动同样生效：治理代码不享有豁免，反而是被管得最严的那部分。

## 系列回顾：一条线

五篇其实只讲了一件事的五个剖面：

1. **声明不是证据**——checkbox 机制上就不携带事实；
2. **门禁必须 fail-closed**——默认值决定一切，口子会被学成主路径；
3. **规则从事故里长**——认知盲区里的错误，只有机械核验抓得住；
4. **归属是前提**——没有归属，receipt 和 scope 都是空话；
5. **治理自身也要被治理**——最后防线用测试和单一事实源守住。

这条线的下一站是把第 1、2、4 篇的机制从"项目纪律"提炼成独立工具：输入 agent 的完成声明 + git diff + 执行观测，输出四值判定。工作名 `claimcheck`，本仓的后续项目。

## 带走的检查清单

- 数数你的门禁规则有几处副本：配置、代码、文档——超过一处，就已经埋了雷；
- 每个事故复盘的固定产出：一条规则 + 一个回归测试，缺一不可；
- 门禁改动是否触发治理套件全量回归？治理代码是否和业务代码走同一套（更严的）门禁？
- 拉一下"不通过"的分类占比：`CONFIG_ERROR` 占比异常时，先修门禁，别急着抓业务质量。
